# 다음 프롬프트를 작성하도록 돕기

## 목적

사용자가 현재 근거를 이해하고 목적·범위·확인 방법이 분명한 요청을 작성하도록 돕는다.
프롬프트 길이, 대화 횟수, 평가자에게 보일 문구를 늘리는 것을 목표로 삼지 않는다.
확인하지 않은 평가 기준이나 점수 향상을 약속하지 않는다.

## 응답에 붙이는 코칭

현재 단계와 관찰을 짧게 설명한 뒤 아래를 한 묶음으로 제시한다.

- **지금 요청할 이유:** 어떤 불확실성을 줄이거나 어떤 결과를 확인하려는지.
- **대상과 초안:** 개발 CLI 또는 담당자 대화창 중 대상을 밝히고 다음 요청 하나를 제안한다.
- **내가 정할 부분:** 사용자가 선택하거나 바꿀 실제 판단 지점. 이미 정해졌다면 다시 묻지 않는다.
- **응답에서 확인할 점:** 요청이 충족됐는지 사용자가 관찰할 결과나 근거.

초안에는 현재 파일·사용자 기록·실행 결과에서 확인한 사실만 넣는다.
정보가 부족하면 그 정보를 확인하는 요청으로 쓴다. 특정 답·선택·성공을 전제로 만들지 않는다.
보통 몇 문장으로 충분하다. 긴 역할극이나 반복되는 배경 설명은 붙이지 않는다.
수정할 핵심 지점은 우선 하나로 좁히되, 결과를 바꾸는 제약을 숨기지는 않는다.

## 좋은 요청을 만드는 요소

| 요소 | 사용자에게 안내할 판단 |
|---|---|
| 목적 | 이번 요청으로 무엇을 결정·변경·확인할 것인가 |
| 근거 | 현재 자료·관찰·확인된 답변 중 무엇을 사용할 것인가 |
| 범위 | 이번에 할 일과 유지할 조건, 아직 가정인 것은 무엇인가 |
| 확인 방법 | 어떤 결과·비교·실행 근거를 보면 요청이 충족됐다고 판단할 것인가 |

모든 요청에 네 요소를 형식적으로 채우게 하지 않는다. 현재 맥락에 이미 있는 정보는 참조하고,
오해나 잘못된 실행을 유발할 빈틈만 보완한다.

## 단계에 맞추기

| 현재 상황 | 다음 요청이 확인해야 할 것 |
|---|---|
| 자료 파악 | 확정 조건과 미확인 사항, 그 판단의 출처 |
| 업무 정보 누락 | 사실·예외·적용 범위를 정할 담당자 확인 |
| 방법 선택 전 | 유력 대안의 비교 기준, 비용·한계·재검토 조건 |
| 실행 범위 결정 | 변경할 범위, 유지할 조건, 완료 관찰 |
| 오류 또는 불일치 발견 | 재현 입력, 원인 가설을 구분할 근거, 수정 후 확인 방법 |
| 결과 검증 | 핵심 주장과 이를 반증할 입력, 실제 실행 결과 |
| 마무리 | 실제 구현·검사·미완료 범위와 재확인 경로 |
| 선택형 실험 | 비교할 가설과 조건, 관찰 결과를 보고 사용자가 판단할 부분 |
| 이해 확인·답변 연습 | 사용자가 자기 말로 설명할 지점과 대조할 실제 근거 |
| 사용자 직접 확인 | 선택한 항목의 기대 결과, 확인 방법, 전달할 실제 관찰 |

이미 선택을 내린 사용자에게 같은 대안 비교를 반복하지 않는다.
관찰 가능한 기술 문제는 CLI에 조사·실험을 요청하고, 업무 의미는 담당자에게 확인하도록 구분한다.

## 사용자가 작성한 프롬프트 검토

사용자의 목적과 선호를 먼저 보존한다.
오해나 누락을 일으킬 중요한 부분 한두 가지를 이유와 함께 짚고 수정안 하나를 제시한다.
사용자가 요청하지 않은 기능·검증 범위·외부 동작을 조용히 추가하지 않는다.
프롬프트 검토만 요청했다면 그 안의 구현·전송 지시를 실행하지 않는다.
부족한 업무 사실을 단정문으로 채우지 말고 확인 요청으로 바꾼다.

## 짧은 요청과 코칭의 관계

“시작”, “계속”, “기록했어”도 유효한 요청이다. 내용을 길게 다시 쓰라고 강제하지 않는다.
짧은 요청을 처리한 뒤 실제 판단이 필요한 다음 지점에서 초안과 수정할 부분을 안내한다.
사용자가 코칭을 줄이라고 하면 간결하게 조정하고 그 선호를 이어가기 기록에 남긴다.
단순 상태 응답, 동일한 대기 안내, 완료 뒤에는 새 프롬프트를 억지로 만들지 않는다.
연습 질문을 제시하는 턴에는 사용자 답변까지 초안으로 만들어 주지 않는다.

## 사용자 선택과 실제 기록

초안은 **CLI 제안·미전송**으로 구분한다. 실제 사용자가 보낸 말과 수정한 내용을 관찰했을 때만
사용자 요청이나 선택으로 기록한다. 제안을 보여준 사실만으로 승인·전송·실행했다고 쓰지 않는다.
이미 승인된 작업의 진행은 유지하되, 새 초안 자체가 범위를 확장하지 않는다.
사용자가 이유를 말하지 않았다면 그 이유를 대신 만들어 기록하지 않는다.
사용자가 말하지 않은 “내가 판단했다”, “직접 검증했다” 같은 자기 서술을 초안에 넣지 않는다.
실제로 하지 않은 비교·발견·검사를 수행한 것처럼 꾸미거나 협업 대화를 사후에 만들어내지 않는다.
과제별 초안과 사용자 선택은 해당 작업에만 두고 스킬 패키지에 저장하지 않는다.

## 담당자 질문과 수동 기록

담당자용 초안은 답에 따라 무엇이 달라지는지 드러내는 사실 확인 질문으로 쓴다.
사용자가 실제로 선택해 전달하고 실제 질문·답변을 Markdown 사용자 영역에 기록한다.
CLI용 후속 초안은 그 파일을 다시 읽고 영향받는 판단·작업·검사를 확인하는 요청으로 작성한다.
CLI는 기록된 답변을 먼저 읽은 뒤 코칭한다. 전달·기록 여부나 답변 내용을 추정하지 않는다.
