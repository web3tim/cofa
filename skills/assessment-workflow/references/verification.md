# 결과를 확인하는 방법

검증의 단위는 중요한 주장이다. 주장마다 입력, 기대되는 관찰, 실행 방법, 실제 결과를 연결한다.
모든 과제에 같은 테스트나 인프라를 강제하지 않는다.

| 확인할 대상 | 적합한 확인 방법 |
|---|---|
| 계산·변환 | 손으로 확인 가능한 작은 입력과 비교, 단위·대상·누락 점검 |
| 제약이 있는 선택 | 반드시 유지할 조건 검사, 간단한 기준안과 같은 입력에서 비교 |
| 분석·해석 | 출처와 계산 재현, 대상·가정 변경에 따른 민감도 확인 |
| 문서·설명 | 근거와 주장 대조, 독자가 필요한 결정을 내릴 수 있는지 확인 |
| 상태가 있는 서비스 | 해당되는 권한·실패·중단·요청 순서·복구 조건 점검 |
| 기존 결과 수정 | 문제 재현, 의도한 변화와 유지해야 할 성질 확인 |

## 검증 계획

필수 조건을 먼저 확인하고, 실패 영향이 큰 경계와 실제 발견한 위험을 추가한다.
각 검사는 어떤 변경이 들어오면 실패해야 하는지 설명할 수 있어야 한다.
테스트 입력은 실제 입력과 구분하고, 필요한 경우 독립적으로 만든 작은 사례를 사용한다.
도구가 없는 검사는 가능한 수동 절차와 확인하지 못한 범위를 적는다.

## 독립성

생성·분석 로직이 스스로 성공을 보고한 것과 결과가 맞는 것은 다르다.
핵심 조건은 결과를 다시 읽거나 다른 계산 경로로 확인할 수 있는지 검토한다.
같은 함수나 가정을 공유한다면 공유하는 부분과 놓칠 수 있는 오류를 적는다.
검증기가 있다면 잘못된 결과를 일부러 넣었을 때 실패하는지도 확인한다.

## 변경에 대한 검사

입력 변화에 대해 유지되거나 바뀌어야 하는 성질을 정한다.
그 성질은 현재 업무 규칙에서 도출해야 하며 그럴듯한 관계를 임의로 가정하지 않는다.
조건을 하나씩 바꾸면 실패 원인과 비용 증가를 구분하기 쉽다.
규모 변화가 중요하다면 시간·메모리·오류율 등 실제 필요한 지표를 측정한다.
측정하지 않은 병목이나 성능을 확정 사실로 말하지 않는다.

## 증거 기록

`EVIDENCE.md`에 조건, 입력 위치, 실행 명령 또는 수동 절차, 기대 결과,
실제 관찰, 결과물 위치, 적용 범위를 남긴다. 명령을 제시한 것만으로 실행했다고 쓰지 않는다.
검증 이후 입력이나 결과가 바뀌면 이전 증거가 여전히 유효한지 판단한다.
필요한 검사만 다시 수행하고, 오래된 증거를 최신 결과의 증거로 표시하지 않는다.
일부 표본을 본 결과를 전체에 대한 검증으로 확대하지 않는다.

검사 상태는 계획 / 작성 / 실행 / 결과 확인 / 무효화 중 맞는 상태를 사용한다.
통과·실패는 실제 결과를 확인했을 때만 기록한다.
